# Deploy on Kubernetes with Helm

[Manual](../README.md) › [Operating the platform](../README.md#operating-the-platform) › **Deploy on Kubernetes with Helm**

> **Start here, then leave.** One Helm chart installs the whole platform on any Kubernetes cluster.
> The chart names no cloud, but getting a cluster ready for it does, so the steps live on one page
> per cloud. Pick yours and follow it top to bottom.

| | |
|---|---|
| **Who** | Whoever holds cluster credentials |
| **Time** | 30 to 40 minutes, most of it waiting for images to pull |
| **You'll end with** | Eight of the nine services Ready, the three apps open in a browser on public HTTPS addresses with a working sign-in, and the MCP server deliberately unready until you register a contract |

## Why one page per cloud, and not one page with branches

Because a reader is only ever on one cloud, and a procedure that asks them to skip half of what
they read is followed at a glance and executed wrong. The concrete version of that: the single page
this replaced told everyone to create an `A` record pointing at the Service's `EXTERNAL-IP`. On
Azure that is right. On AWS there is no `EXTERNAL-IP` to read and no address that stays still, so
the instruction sends the reader looking for something that does not exist.

The split is not even. Between AKS and EKS only the first two steps genuinely differ. Kyma differs
more, because it publishes through a service mesh rather than a load balancer, and a mesh changes
what the pods look like and how they reach each other.

| | AWS EKS | Azure AKS | SAP BTP Kyma |
|---|---|---|---|
| Getting a kubeconfig | `aws eks update-kubeconfig`, and an MFA session if the account demands one | `az aks get-credentials` | **Downloaded** from the BTP cockpit, signing in through a browser with a `kubectl` plugin |
| Default StorageClass | **You create it.** A stock cluster has none and the volumes never bind | Already there | Already there |
| Placing a load balancer | **You tag the public subnets.** Untagged, a Service never gets an address | Already there | **None needed.** The addresses ride the cluster's own gateway |
| Getting a public hostname | Generated by the load balancer, so it is unknown until the Services exist. Two passes | Asked for and granted up front. One pass | A name under the cluster's wildcard, known up front. One pass |
| A free certificate | **No.** Load balancer names are not certifiable by any authority. Self-signed, or bring a domain | Yes, Let's Encrypt issues for the free Azure name | Yes, the cluster's own wildcard certificate, with nothing to issue or renew |
| A service mesh | None | None | **Istio, with mutual TLS required.** The namespace joins it before the install, and every pod runs a sidecar |
| Cost of publishing | About 73 USD a month, four load balancers | About 14.60 USD a month, four public IPs | Nothing: no load balancer |

Everything after that is the same on AKS and EKS, and most of it on Kyma. The passages that are
the same are byte-identical by machine rather than by discipline: `scripts/docs_shared_blocks.py` fails the build when a step
repeated across the runbooks stops agreeing with its other copies.
