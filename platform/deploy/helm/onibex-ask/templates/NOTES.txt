{{- if and .Values.keycloak.enabled (not .Values.keycloak.production) }}

WARNING: Keycloak is running start-dev, which is explicitly not a production
mode and keeps its state in an embedded file inside the pod. Every user, client
and realm change is lost when the pod is replaced. Set keycloak.production=true
with a real database before anyone depends on this.
{{- end }}
{{- if and .Values.keycloak.enabled (not .Values.keycloak.realmImportSecret) (not .Values.keycloak.realmImportConfigMap) }}

WARNING: Keycloak is starting with NO realm to import, and this is the last
moment it is cheap to fix. A realm is read on a first boot only, so this pod is
about to write an empty datastore to its volume and adding
keycloak.realmImportSecret afterwards will change nothing: the file is mounted
and ignored, with no error anywhere. Every sign-in then fails with "Realm does
not exist" while this pod reports perfectly healthy.

Build the realm now, before this pod finishes starting:

  python scripts/make_realm_import.py --password '<one with 8+ chars, a digit and a capital>' \
    --host studio=https://<studio host> --host chat=https://<chat host> \
    --host setup=https://<setup host> --out ./realm.json
  kubectl -n {{ .Release.Namespace }} create secret generic ask-realm \
    --from-file=ask-platform-realm.json=./realm.json && rm ./realm.json

If it already wrote one, the volume has to go:

  kubectl -n {{ .Release.Namespace }} scale deploy {{ include "onibex-ask.fullname" . }}-keycloak --replicas=0
  kubectl -n {{ .Release.Namespace }} delete pvc {{ include "onibex-ask.fullname" . }}-keycloak
{{- end }}

The three things to check first when a pod does not reach Ready:

  1. kubectl -n {{ .Release.Namespace }} logs deploy/{{ include "onibex-ask.fullname" . }}-studio
     The SPA entrypoint names the missing variable and stops rather than serving
     a login page that points nowhere.

  2. Is the encryption key the SAME one this environment was installed with?
     A changed key is not a rotation, it is a data-loss event: every stored
     credential stops decrypting and has to be entered again in ASK Setup.

  3. Does auth.publicUrl match the issuer in the tokens? A mismatch shows up as
     every request being rejected while the pods report healthy.
